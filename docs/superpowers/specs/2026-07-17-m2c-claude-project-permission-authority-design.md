# M2c Claude Project Permission Authority Design

**Date:** 2026-07-17
**Status:** Approved for implementation under the active completion goal
**Milestone:** Phase 3 M2c real four-stage acceptance closure
**Scope:** Disposable live-project permission-mode authority only

## 1. Purpose

Frozen implementation `79d8160eb60ad4e8bfb37ff43615f099afd9edc5`
passed deterministic verification, two complete suites, and strict preflight
v6. Its separately authorized real Mission crossed Leader Preview, daemon
admission, Claude ACP admission/prompt, and completed step 1, but terminated as
`first_attempt_terminal_contract_invalid`: the Claude ACP attempt succeeded and
one Worker reply was durable while no permission request or handoff existed.

Read-only inspection shows that the installed Claude ACP adapter resolves
user/project/local settings through the Claude SDK and derives session
permission mode from `permissions.defaultMode`. The repository's existing Phase
2 real ACP vertical slice explicitly writes a disposable project-local
`.claude/settings.local.json` with `defaultMode=default` so a user-level
permissive/auto mode cannot bypass the permission bridge. M2c omitted that
deterministic input.

This design gives the disposable M2c project a closed, exact, project-local
Claude permission authority before any ACP process starts.

## 2. North-star alignment

- AgentDeck's acceptance evidence must prove the permission bridge, not inherit
  an unrelated user preference that can suppress it.
- The fix is local-first and disposable. It never reads, changes, copies, or
  reports user/global Claude settings.
- ACP remains the Worker transport and AgentDeck remains the governance edge.
- The setting is explicit, content-addressed, mode-restricted, revalidated, and
  removed with the disposable project.
- No retry, timeout inflation, prompt manipulation, provider fallback, or
  transcript inspection is introduced.

No production `src/agentdeck/**` behavior changes in this slice.

## 3. Alternatives

### 3.1 Retry or strengthen the natural-language instruction

Rejected. The successful no-permission attempt is deterministic evidence that
permission policy, not wording or timing, controlled the callback path.

### 3.2 Force `default` in generic `AcpTransport.new_session()`

Rejected for this slice. ACP session mode IDs are agent-defined. Hard-coding a
Claude-specific mode in the generic transport would change all ACP agents and
requires its own product/configuration/contract design. A future AgentDeck
session-mode governance feature may expose an explicit per-agent policy, but it
must not be smuggled into M2c acceptance.

### 3.3 Pin exact project-local settings in the disposable M2c project

Chosen. This matches the repository's already validated Phase 2 real ACP
practice, is supported by the installed adapter, leaves user settings untouched,
and constrains only the fixed Claude-specific acceptance scenario.

## 4. Exact settings contract

Before live configuration or any ACP/Leader process starts, the harness creates:

```text
.claude/                         directory, mode 0700
.claude/settings.local.json     regular non-symlink file, mode 0600
```

The file bytes are exactly:

```json
{"permissions":{"defaultMode":"default"}}
```

followed by one LF byte. No indentation, alternate key order, additional keys,
or platform newline is accepted.

Creation uses exclusive, no-follow semantics inside the already-proven
disposable project. Any pre-existing `.claude`, path collision, symlink,
special file, wrong owner/mode, short write, or unexpected entry fails closed as
`claude_permission_settings_invalid`. The helper never resolves or accesses the
user home or `CLAUDE_CONFIG_DIR`.

## 5. Runtime seal

Successful creation returns an in-memory seal containing only filesystem
identity and content facts for the project-local directory/file:

- device and inode;
- owner;
- exact mode;
- file size;
- SHA-256 of the exact file bytes.

The seal contains no absolute path and is never printed or persisted. The
harness revalidates it:

1. immediately after creation;
2. before Leader/Mission creation;
3. after the first pending permission is durable;
4. before and after every explicit permission confirmation;
5. before takeover/return-control boundaries;
6. after Mission completion and before evidence projection.

Replacement with identical bytes, chmod, content change, symlink substitution,
directory replacement, or extra `.claude` entry fails closed with the same
fixed code. No weakened recovery or recreation is allowed after drift.

## 6. Authority and contract boundaries

Tool authority stays `m2c-tool-authority/v3`; strict preflight stays
`m2c-live-preflight/v6`. The project-local settings are generated by the frozen
acceptance implementation after preflight and are not installed tool identity.
Their authority is bound by the new frozen git SHA plus the in-process runtime
seal.

The old `79d8160e...` SHA/model/digest live authority is exhausted. Even if the
installed tool digest remains unchanged, a new frozen SHA requires two fresh
complete suites, one new designated v6 preflight, and a separately authorized
one-shot live Mission.

## 7. TDD requirements

RED must prove that current `_write_live_config()` does not create a
project-local `default` permission setting. GREEN must cover:

1. exact directory/file bytes and modes;
2. exclusive creation and no user/global settings access;
3. pre-existing directory/file/symlink/special-file rejection with no overwrite;
4. content, mode, inode, owner, kind, symlink, directory, and extra-entry drift;
5. identical-byte inode replacement rejection;
6. seal contains no path or settings content;
7. live setup obtains and revalidates the seal before ACP admission and across
   every permission/governance boundary;
8. settings are removed by existing whole-project cleanup on success, failure,
   and interruption;
9. no change to authority v3 digest, preflight v6 shape, timeouts, retry, or
   product source;
10. real nodes remain opt-in skipped in deterministic/full suites.

## 8. Verification sequence

1. Commit one exact RED test separately.
2. Implement the minimal settings creation/seal/revalidation path and focused
   drift/leakage tests.
3. Update SOP, validation, handoff, HISTORY, and this plan.
4. Run focused settings/live-setup tests, complete non-live M2c, product and
   Conversation regressions, compile, diff, leakage, process, worktree, and
   temporary-root audits.
5. Freeze one new implementation SHA and run two complete suites in fresh
   detached worktrees with absolute `PYTHONPATH`.
6. Re-audit unchanged installed inputs and restored Claude authentication.
7. Run exactly one new strict v6 preflight.
8. Only a ready result may support one separately authorized real Mission.
9. Never retry any exhausted authority.

## 9. Completion criteria

This slice is complete when the disposable project's Claude permission mode is
created and held under exact runtime authority, all deterministic/full
verification passes, and a new v6 preflight is ready. M2c completes only when
the subsequent real Mission proves two explicit ACP permissions, all four
stages/handoffs, artifact bytes/hash, governance/recovery evidence, and zero
residue. M3 remains locked until that PASS.
